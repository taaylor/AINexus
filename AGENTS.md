# Разделение слоёв

Правила относятся к сервисам в `services/`. Для новых модулей сохраняйте существующую структуру слоёв: `presentation`, `application`, `domain` и `infrastructure`. Слой сборки приложения находится в `bootstrap`.

## Направление зависимостей

- Внутренние слои не импортируют внешние: `domain` не зависит от `application`, `presentation` или `infrastructure`; `application` не зависит от `presentation` или `infrastructure`.
- `presentation` вызывает сценарии `application` и преобразует HTTP-ввод и результат сценария в API-схемы.
- `application` координирует сценарии использования и обращается к нужным абстракциям внутренних слоёв.
- `infrastructure` реализует работу с внешними системами и зависит от тех внутренних контрактов, которые реализует.
- `bootstrap` собирает приложение и связывает реализации с их потребителями. Не размещайте там бизнес-правила.

## Ответственность слоёв

### `domain`

- Хранит бизнес-модели, правила, инварианты и понятия предметной области.
- Содержит доменные контракты, если они выражают понятие предметной области или нужны доменной логике.
- Не содержит типов HTTP, SQLAlchemy, Pydantic, JWT-библиотек и других деталей реализации.

### `application`

- Содержит сценарии использования и координирует доменные модели и порты.
- Объявляет контракты внешних возможностей, когда ими пользуется сценарий приложения и они не являются доменными понятиями.
- Может содержать DTO сценариев использования. Не переносите такие DTO в домен, если они нужны только для обмена данными между слоями.

### `presentation`

- Отвечает за транспортный протокол, HTTP-маршруты, валидацию входа и API-схемы.
- Преобразует API-схемы в команды/запросы application-слоя, а результаты сценариев — в ответы API.
- Не содержит бизнес-правил и не обращается напрямую к инфраструктурным адаптерам.

### `infrastructure`

- Содержит адаптеры к базе данных, криптографии, файловым и сетевым системам и сторонним библиотекам.
- Реализует порты внутренних слоёв. Адаптер может создавать и возвращать внутренние модели, но не должен объявлять контракт, от которого зависят внутренние слои.
- Преобразует модели внешних библиотек и хранения во внутренние модели на границе адаптера.

## Где размещать модели и контракты

Размещайте тип по смыслу и владельцу контракта, а не по месту, где он создаётся:

- Доменная сущность или объект-значение — в `domain/entities`.
- DTO конкретного сценария использования — в `application/dto`.
- Схема запроса или ответа API — в `presentation/api/.../schemes`.
- ORM-модель, модель сторонней библиотеки или формат хранения — в соответствующем модуле `infrastructure`.
- Порт должен находиться во внутреннем слое, который владеет потребностью; инфраструктурный адаптер реализует этот порт.

## Именование контрактов и работа через интерфейсы

- Для use case `<Action>` называйте API-схемы `User<Action>InputSchema` и `User<Action>OutputSchema`. Например, для регистрации: `UserRegisterInputSchema` и `UserRegisterOutputSchema`.
- DTO того же сценария называйте без суффикса `Schema`: `UserRegisterInput` и `UserRegisterOutput`. Схемы остаются в `presentation`, DTO — в `application`; преобразование между ними выполняется явно на границе слоёв.
- Схема используется только на endpoint-границе. Use case принимает application DTO, например `UserRegisterInput`, а не Pydantic-схему.
- Параметр endpoint, содержащий тело входящего запроса, называйте `input_data`, а не `request`.
- `BaseSchema` предоставляет generic `def to_dto[TDto](self, dto_type: type[TDto]) -> TDto` с синтаксисом generics Python 3.12: берёт Python-значения из схемы, выбирает совпадающие `init=True` поля dataclass DTO и создаёт DTO через `TypeAdapter`. Schema-only поля, например `password_repeat`, в DTO не передаются; отсутствующие обязательные поля DTO должны приводить к ошибке валидации. Для этого не использовать `TypeVar`.
- Endpoint передаёт тип DTO явно: `input_data.to_dto(UserRegisterInput)`. Схема не импортирует конкретный DTO. Если имена полей схемы и DTO различаются, преобразование задаётся явно на границе, без неявного переименования.
- Для ответа endpoint преобразует application DTO в output schema через `OutputSchema.model_validate(output_dto)`; базовая схема настроена на `from_attributes=True`.
- Каждый use case наследуется от generic-интерфейса `IUseCase[Input, Output]` из `domain/ports/usecase.py` и реализует `execute(*, input_data: Input) -> Output`.
- Слои и обработчики зависят от интерфейсов потребляемых операций, а не от конкретных реализаций. Это относится к use cases, репозиториям, хэшерам и `UnitOfWork`.
- Имена методов репозитория описывают операцию или критерий, не повторяя сущность репозитория: используй `create` и конкретные имена условий, например `exist_by_username_email`, вместо `create_user` или `create_credentials`.
- Конкретные реализации связываются с интерфейсами в `bootstrap` через DI. Не внедряйте конкретный infrastructure-класс непосредственно в `presentation` или application-сценарий.

`TokenPair` является доменной моделью и должен находиться в `auth/domain/entities/tokens.py`. Инфраструктурная реализация генерации токенов может создавать и возвращать `TokenPair`, импортируя его из домена. Не объявляйте вторую копию этого контракта в инфраструктуре. JWT-кодирование и вызовы JWT-библиотеки остаются деталями инфраструктуры.

Не используйте `common` как место для моделей, которые принадлежат конкретному слою или сценарию. Не дублируйте одну модель в нескольких слоях: вместо этого явно преобразуйте её на границе, если внешнему слою нужен собственный формат.

## Стиль тестов

- Размещайте тесты в `services/<service>/tests/` по проверяемому уровню или сценарию. Для auth функциональные HTTP-тесты находятся в `services/auth/tests/functional/`.
- Один тест проверяет один сценарий и его наблюдаемый результат. Дополнительные проверки допустимы, если вместе они подтверждают этот результат, например HTTP-ответ регистрации и появление созданных записей.
- Называйте тесты точно и предметно по шаблону `test_<сценарий>_<условие>_<ожидаемый_результат>`. Из имени должно быть понятно, что проверяется и при каком условии. Избегайте общих имён вроде `test_success`, `test_error` и `test_invalid`; например, используйте `test_user_login_invalid_password_returns_unauthorized`.
- Для параметризованных сценариев задавайте понятные `id` в `pytest.param`, чтобы имя каждого случая было видно в выводе pytest.
- Фикстуры запрашивайте параметрами теста или других фикстур. Не вызывайте функцию фикстуры напрямую и не дублируйте её подготовку вручную.
- Используйте фикстуры для повторно используемой подготовки и ресурсов. Не выносите в фикстуру простые значения, если это скрывает важные для сценария данные; подготовка должна оставаться понятной из теста.
- Фикстура по умолчанию имеет функциональную область действия. Используйте `session` только для дорогих общих ресурсов или неизменяемых объектов; `autouse` оставляйте для действительно общей настройки набора тестов.
- Именуйте фикстуры по предоставляемому объекту или ресурсу (`user`, `user_cred`, `client`), а фикстуры-фабрики — с суффиксом `_factory`. Фикстуры-фабрики должны принимать необходимые переопределения, чтобы тест задавал только значимые для сценария поля.
- Создавайте валидные тестовые данные через фабрики из `tests/factories.py`, а уникальные или случайные значения — через `faker`. Не фиксируйте случайные значения вручную без необходимости.
- Для тестовых записей используйте существующие фабрики и фикстуры доступа к БД, например `user_factory`, `user_cred_factory` и `active_session`. Не связывайте тест с порядком запуска других тестов и создавайте нужное состояние в самом тесте или его фикстурах.
- В функциональных тестах вызывайте API через `client` или подходящую авторизованную фикстуру. Проверяйте код ответа и значимое тело через `assert_response`/`assert_nodata_response`; если сценарий меняет состояние, отдельно проверяйте это состояние через тестовую сессию.
- Для асинхронных тестов используйте `async def` и общий `pytestmark = pytest.mark.anyio`, если весь модуль состоит из асинхронных тестов.
